# HW1: аналитическая модель производительности CNN

Сеть из шести свёрток (7x7 s2 → maxpool → 5x5 → 3x3 s2 → 1x1 → 3x3 s2 → 1x1),
global average pooling и голова из двух Linear. FP32, `eval()` + `inference_mode()`.

## Формулы

S — сторона картинки, B — размер батча.

- **FLOPs** $= B\,(17\,712\,S^2 + 313\,344)$. Свёртки дают $8856\,S^2$ MAC на картинку, Linear ещё 156 672, умножаем на 2.
  На всех конфигурациях совпадает с `torch.utils.flop_counter` один в один.
- **Memory** $= 13\,729\,552 + 68\,B S^2$ байт. Это веса (4 161 296), workspace cuBLAS/cuBLASLt,
  который PyTorch держит после первого Linear (9 568 256 = 2×4 МиБ + 8×16 КиБ + 1 МиБ), и активации.
  Пик по активациям внутри maxpool: вход x (12 Б/px) + выход conv1 (32) + выход пула (8) + индексы int64 (16).
- **Трафик** $= B\,(380\,S^2 + 8592) + 4\,161\,296$ байт: каждый из 17 kernel-ов один раз читает вход и веса и один раз пишет выход.
- **Latency** $= \sum_{k=1}^{17} \max(t_{op},\ F_k/P,\ Q_k/BW)$: каждый kernel упирается либо в запуск, либо в арифметику, либо в память.
- **Energy** $= P_{static}\cdot T + e_{flop}F + e_{byte}Q$.

Подобранные параметры (`results/theta.json`):

- latency: `t_op = 32.2 мкс`, `P = 4.56 TFLOP/s`, `BW = 109 ГБ/с`
- energy: `P_static = 54.1 Вт`, `e_flop = 4.09 пДж/FLOP`, `e_byte = 0`

## Обсуждение

Про запуск. На маленьких входах время почти не зависит ни от S, ни от B: при B = 1 один проход
занимает 0.54–0.68 мс вплоть до S = 176. Всё это время GPU в основном ждёт, пока Python и PyTorch
поставят в очередь следующий kernel. Фит дал t_op ≈ 32 мкс на kernel, 17 kernel-ов как раз дают
0.55 мс. Для десктопа это много, но в Colab процессор слабый и общий, так что я не удивился.
По модели при B = 1 сеть перестаёт быть launch-bound примерно на S ≈ 336.

Про память. ReLU, maxpool и avgpool ничего не считают, только гоняют тензоры: 232 из 380 Б/px
всего трафика приходится на них. Свёртки с большими весами (у conv5 2.4 МБ) при маленьком B·S²
тоже упираются в память, потому что прочитать веса дольше, чем посчитать MAC. Это хорошо видно
на `kernel_regimes.png`, где каждый kernel по мере роста батча проходит launch → memory → compute.
При этом сеть целиком memory-bound не становится никогда: у всех свёрток интенсивность 43–267 FLOP/B,
а точка перегиба по фиту 42 FLOP/B. Сам BW = 109 ГБ/с (треть от паспортных 320) я бы
не воспринимал всерьёз: memory-bound kernel-ы занимают малую долю общего времени, и фит их почти не видит.

Про вычисления и 70 Вт. На больших входах время растёт линейно с FLOPs. Я ожидал P ближе
к 8 TFLOP/s, но потом посмотрел на частоты в CSV. T4 почти весь прогон сидела на своём лимите
70 Вт (медиана 67 Вт) и сбрасывала частоту, чтобы в него уложиться: 1245 МГц при B = 1 и около
795 МГц при B ≥ 128, при boost 1590. На медианной частоте пик FP32 всего около 4.9 TFLOP/s, и
подобранные 4.56 уже довольно близко к нему. Реально на больших конфигурациях сеть выдаёт около 2.6 TFLOP/s.

Где ломается latency. P в модели один на всю сетку, а частота плавает, поэтому на больших батчах
модель слишком оптимистична: медианная ошибка +4 % при B < 128 и −27 % при B ≥ 128. Вторая причина
в cuDNN. С `benchmark=False` он сам выбирает алгоритм по эвристике и на большом батче переключается.
При S = 32 переход с B = 64 на B = 128 увеличивает работу вдвое, а время втрое. Именно в этих же
конфигурациях появляется лишняя память (см. ниже), так что это, скорее всего, один и тот же
переход на другой алгоритм. Углы от `max()` тоже дают ошибку, но меньшую: в реальности
запуск и счёт перекрываются, и переход между режимами плавный.

Где ломается память. В 28 конфигурациях из 132 формула совпала с замером с точностью до 240 байт
(это округление аллокатора). Отсюда видно, что и 68 Б/px с индексами maxpool, и 9.125 МиБ под cuBLAS
угаданы правильно. В остальных точках замер больше, потому что cuDNN выделяет workspace под свой
алгоритм. На больших B·S² это около 32 Б/px (до 1.5 ГиБ при S = 512, B = 256), при S ≤ 128 и маленьком
батче это несколько МиБ. При S = 32–64 и B ≥ 128 он снова растёт, в тех же точках, где скачет latency.
Из одной архитектуры это не выводится, поэтому формулу стоит считать нижней границей. Единственная
конфигурация, где формула дала больше замера (S = 256, B = 2), была измерена первой, и буферы
cuBLAS к тому моменту ещё не были выделены. В следующий раз я бы делал прогрев перед замером памяти.

Про энергию. Мощность почти постоянная, поэтому энергия в основном повторяет время:
P_static·T даёт 82 % предсказанной энергии для медианной конфигурации, и ошибки energy почти те же,
что у latency. e_byte получился нулевым не из-за бага. На этой сетке FLOPs и байты растут одинаково,
оба как B·S², корреляция > 0.999999, и регрессия просто не может их разделить. Весь динамический
вклад ушёл в e_flop. Батч всё равно выгоден: при S = 224 одна картинка стоит 32.1 мДж с B = 1
и 17.4 мДж с B = 32.
